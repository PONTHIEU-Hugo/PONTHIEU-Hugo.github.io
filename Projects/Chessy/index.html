Sur cette page

    Objectif

    L'objectif de ce projet était de concevoir un DSL (Domain Specific Language) en binôme, dans un temps imparti de 2 semaines. Derrière cet objectif de rendu, le projet visait à nous apprendre le fonctionnement d'un CPU. Pour cela, nous avons dû prendre en compte les temps d'accès aux différentes mémoires, la programmation en MASM et le SIMD. À cela s'est ajouté le développement du DSL lui-même, avec sa pipeline complète : Lexer, Parser, analyse sémantique, compilation en bytecode et machine virtuelle.

    Notre ambition, à mon binôme et moi, était de faire un langage pensé pour la recherche en profondeur d'une IA d'échecs. L'idée : écrire l'algorithme de recherche dans un langage simple et lisible, tout en confiant les opérations coûteuses (génération des coups, bitboards) à du C++ natif. L'objectif final était de pouvoir jouer contre une IA entièrement écrite en Chessy.

    Fonctionnement

    Le langage

    Chessy est un langage typé statiquement, avec des fichiers à l'extension .chessy. On y retrouve les types entiers classiques (I8 à I64, U8 à U64), les booléens, mais surtout des types propres aux échecs : Bitboard, Square, Piece et Move. Les fonctions se déclarent avec func et indiquent leur type de retour après :. Voici par exemple le cœur de notre IA, un alpha-beta en négamax écrit directement en Chessy : 

    func AlphaBeta(I32 depth, I32 alpha, I32 beta) : I32 {
          if (depth == 0) {
              return Quiescence(alpha, beta, 0);
          }

          Generate();
          SortMovesMvvLva();
          I32 moveTotal = MoveCount();

          if (moveTotal == 0) {
              if (InCheck(SideToMove())) {
                  return -100000;
              }
              return 0;
          }

          I32 bestScore = -1000000;
          I32 moveIndex = 0;

          do {
              Move currentMove = MoveAt(moveIndex);
              MakeMove(currentMove);
              I32 score = -AlphaBeta(depth - 1, -beta, -alpha);
              UnmakeMove();

              if (score > bestScore) { bestScore = score; }
              if (score > alpha)     { alpha = score; }
              if (alpha >= beta)     { moveIndex = moveTotal; }
              moveIndex = moveIndex + 1;
          } while (moveIndex < moveTotal);

          return bestScore;
}

    La pipeline

    Un fichier Chessy passe par cinq étapes avant d'être exécuté. Le Lexer lit le fichier entier en mémoire et le découpe en tokens qui pointent directement dans ce buffer, sans copie de chaîne. Le Parser construit ensuite l'arbre syntaxique ; pour les expressions, il s'appuie sur des « binding powers » (Pratt parsing), qui gèrent la priorité des opérateurs sans multiplier les règles de grammaire. L'Analyser vérifie la sémantique : portée des variables, types des opérations, nombre et types des arguments passés aux fonctions. Le Compiler traduit enfin l'arbre en bytecode, que la machine virtuelle exécute.

    Sur cette pipeline, je me suis occupé du Lexer, du système de tests et de la machine virtuelle ; mon binôme a pris en charge le Parser, l'Analyser, le Compiler et les fonctions natives d'échecs.

    La machine virtuelle

    Nous avons choisi une VM à registres plutôt qu'une VM à pile. Une VM à pile empile et dépile sans arrêt ses opérandes, alors qu'une VM à registres fait le même travail en moins d'instructions : chaque instruction indique directement où lire ses opérandes et où écrire son résultat. La nôtre possède 256 registres, et chaque instruction est composée d'un opcode et de trois opérandes (A, B, C). Le jeu d'instructions compte une trentaine d'opcodes répartis en familles : accès mémoire (MOV, LOAD, STORE…), arithmétique, opérations bit à bit, comparaisons, sauts conditionnels et appels de fonctions.

    Comme le langage manipule plusieurs types, une addition entre un I32 et un I64 n'exécute pas le même code qu'une addition entre deux U8. Plutôt que d'enchaîner des conditions à chaque opération, la VM utilise des tables de pointeurs de fonctions indexées par le type des deux opérandes. Ces tables sont générées à la compilation du C++ (constexpr et std::index_sequence) : à l'exécution, choisir la bonne opération ne coûte qu'un accès à un tableau.

    Pour les appels de fonctions, chaque appel crée une frame sur une pile dédiée, qui mémorise le début de ses variables locales et sa propre liste de coups. Cette liste par frame est indispensable à la récursion de l'alpha-beta : chaque niveau de profondeur génère ses coups sans écraser ceux du niveau supérieur. Au retour, la valeur est placée dans le registre 0 et l'exécution reprend là où elle s'était arrêtée.

    Les fonctions natives

    Interpréter chaque calcul de bitboard dans la VM aurait été bien trop lent. Chessy expose donc une trentaine de fonctions natives écrites en C++ et appelées via une instruction dédiée (CALL_NATIVE) : génération des coups, MakeMove / UnmakeMove, attaques des pièces, PopCount, tri des coups MVV-LVA… La répartition est simple : la logique de recherche reste en Chessy, lisible et modifiable, et le calcul lourd reste en C++.

    Les tests

    Pour éviter de casser une étape en modifiant la précédente, nous avons mis en place une pipeline de tests qui couvre chaque étape : Lexer, Parser, Analyser et compilation. Elle s'appuie sur des fichiers .chessy dédiés (déclarations, opérations mathématiques, booléennes et binaires, boucles, fonctions) et vérifie que chacun produit exactement les tokens, l'arbre ou le bytecode attendus.

    Difficultés rencontrées

    La plus grosse difficulté a été l'assemblage de la pipeline. Le Compiler et la VM ont été développés en parallèle, chacun de notre côté, sans format de bytecode fixé à l'avance. Au moment de les fusionner, le bytecode produit par le Compiler ne correspondait pas toujours à ce qu'attendait ma VM : ordre des opérandes, registre de la valeur de retour, gestion des arguments lors des appels. Il nous a fallu plusieurs merges et de nombreux correctifs avant d'obtenir un premier programme qui s'exécute de bout en bout.

    Résultat

    Au bout des deux semaines, Chessy fonctionne de bout en bout : un fichier .chessy est analysé, compilé puis exécuté par notre VM. Notre programme principal, entièrement écrit en Chessy, contient un alpha-beta avec quiescence search et tri des coups MVV-LVA, et permet de jouer contre l'IA directement dans le terminal.
